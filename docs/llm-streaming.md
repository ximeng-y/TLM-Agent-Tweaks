# LLM 流式请求与断流回退

在 [`llm-protocol-adapters.md`](llm-protocol-adapters.md) 的三协议边界之上，本 mod
把 TLM 原有 LLM 出口换成「优先流式、必要时非流式回退」的传输状态机。调用方仍是
TLM 原有接口（`LLMOpenAIClient#chat` / `LLMCallback`），消息、工具、历史与失败
回调语义不变，其他 mod 不需要改动。

## 语义

- 每个逻辑请求最多发出 **5 次 HTTP**：首次 `stream:true` + 响应头前断连的流式重发 1 次
  + 状态码重试 2 次 + 非流式回退 1 次；三条路径各自计数，互不占用对方额度。
- 回退不是续传：不重放、不重跑已经执行过的工具轮次，也不改变输入与工具结果快照。
- 中间失败对外隐藏，调用方只在最终结果上收到一次 `handle`（成功或失败）。
- `stream_options.include_usage` 只用于 Chat Completions；Responses 与 Anthropic
  Messages 只发送 `stream:true`。

## 三条重发路径

| 失败场景 | 判定依据 | 行为 | 额度 |
| --- | --- | --- | --- |
| 响应头前失败（含单次尝试超时） | 流式请求未收到响应头 | 保持 `stream:true` 重发一次；额度用尽后改用非流式 | 独立 1 次（受 `retry.enabled` 控制） |
| 正文读取中途失败 | 已收到响应头，但正文未完整取回 | 改用 `stream:false` 重发一次 | 独立 1 次（始终生效） |
| 429 / 5xx | HTTP 状态码 | 保持当前模式重发 | 状态码重试 2 次 |

两条传输路径都只看本次尝试自己记录的事实，不看异常类型、也不看响应头声明的内容类型：

- 响应头前失败的判定不依赖异常类型：单次尝试的超时由截止计时器作废在途连接，
  `send.join()` 随之抛出没有语义的取消异常，只看类型会把最常见的「服务端在响应头前挂起
  直到超时」误判成调用方取消。改用本次尝试自己记录的两项事实——是否已收到响应头、是否被
  截止计时器作废。
- 正文阶段的判定不依赖 `Content-Type`：流式端点返回 `application/json` 时响应头同样已到，
  正文一样可能读到一半卡死，那是传输失败而不是协议错误，仍然允许一次非流式回退。
  分界是「正文是否完整取回」——完整取回之后才失败的只剩解码，属于协议问题，不重发也不回退。

## 三种情况回退

1. 服务端**明确表示不支持** `stream` / `stream_options`：HTTP 400/415/422 且响应体
   包含 stream 相关的 `not support` / `unsupported` / `unknown` / `invalid` 等字样。
2. **正文读取中途失败**：已收到响应头后连接中断、读 body 超时、缺少协议终止标志
   （`[DONE]` / `response.completed` / `message_stop`）或分片聚合失败。响应头是
   `text/event-stream` 还是 `application/json` 都一样。
3. **响应头之前失败且传输重试额度已用尽**：保持流式重发一次仍失败之后，再改用非流式。
   已建立连接、服务端只是不对流式请求回响应（流式端点挂起、网关对 SSE 挂起）就属于这种
   情形，此时普通请求常常是通的，回退是唯一能拿回成功响应的路径。

只有在服务端**明确**不支持流式时才回退的分工见上表；`retry.enabled=false` 时响应头前失败
不重发，直接落到第 3 条的回退。

以下情况**不进行非流式重试**：

- 401 / 403 / 404 / 429；
- 普通 400 / 422 / 5xx（没有 stream 不支持提示）；这些 HTTP 错误交给 TLM 原失败处理；
- 流式请求返回的普通 JSON（`application/json`）**完整到达但解码失败**：属于协议错误，
  直接按失败上报，不再请求；
- 调用方主动取消（实体移除、离开世界、服务器停止），取消不回退、不触发
  `onFailure`。

## 读取与时限

- 增量读取使用 JDK `HttpClient` + `BodyHandlers.ofInputStream()` 真正按字节流读取，
  不使用 `ofString` 伪流式。
- SSE 解帧支持 UTF-8 跨字节块、CRLF/LF/CR、空行分帧、注释、多行 `data`、分片边界；
  尾部缺少空行的残片不会伪造成事件。
- 收到协议终止标志后立即收口，不等待 keep-alive 连接的 EOF。
- 已获得响应头后的 body 读取由独立截止计时器保护：超时会关闭 `InputStream` 并让本次
  attempt 作废，不依赖 `HttpRequest.timeout` 单独兜底。
- 每个 attempt 独占连接、响应流和计时器，并有一次性终结状态；旧尝试只能关闭自己的
  资源，不会关闭新的回退连接，也不会在终结后再发增量或提交聚合元数据。

## 只读增量事件

- 增量、回退、完成、失败、取消事件通过服务端只读事件中心
  （`ProtocolStreamHub`）发布，订阅者只能读，且抛出的异常被隔离，不影响请求。
- 每个事件都携带按请求捕获的不可变上下文：女仆 UUID、站点 ID、维度、等待气泡 ID。
- 只有最终完整成功结果（包括非流式回退成功）才会提交协议原始历史；断流片段不会
  污染回退后的历史或 opaque 元数据。

## 思考链气泡显示

增量事件中只有**思考增量**会被转发到客户端，用于「少女思考中」等待气泡内的单行滚动
展示（见 [docs/thinking-bubble.md](thinking-bubble.md)）。该展示是纯视觉层：

- 不向聊天栏、历史记录或 TTS 注入任何增量文本，模型的**答案**增量不参与显示；
- 响应头前失败的流式重发成功后，思考从空窗口继续滚动：重发仍是流式，`REASONING_DELTA`
  正常产生；
- 回退发生时（以及回退后进入的普通模式阶段）**不补播**中断前已收到的思考片段，
  气泡立即清空并切回原生提示文本，避免把中断的流式片段当作有效输出；
- 请求结束、失败、取消时清空，不残留上一次的思考内容。

## 生命周期

- 服务端实体移除/离开世界（`EntityLeaveLevelEvent`）按女仆 UUID 取消其在途请求，
  客户端实体卸载不影响服务端请求；
  服务器停止（`ServerStoppingEvent`）取消全部在途请求。
- 取消会关闭网络连接与截止计时器并清理登记表，异步任务不长期持有世界或女仆对象，
  避免残留回调污染重进世界后的对话。
- 取消登记按不可变的 maid UUID 过滤当前在途请求，不维护可并发读写的二级索引。

## 已知限制与风险

- **重复计费风险**：流式请求中断后回退会再发一次非流式请求，服务端可能对两次请求
  分别计费；中断那次流式尝试的用量对客户端不可见，因此不伪造 0 或精确费用。
- 用量只使用服务端真实返回的数据，缺失就保持缺失；不回填、不估算。
- 回退只发生一次；回退之后再次失败就向调用方上报最终失败（状态码重试与传输重试
  各自的额度仍在此前生效）。
- 未在真实 Minecraft 客户端/服务器实机验证，也未用真实付费端点验证流式行为；
  自动测试使用 JDK 内置 `HttpServer` 模拟流式与断流。
